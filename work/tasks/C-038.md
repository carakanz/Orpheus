# C-038 — ограничить отправку куч за такт (хвост C-035)

## Зачем
Хвост C-035 (`work/next.md`, строка C-035): `SendPilesTo` (`src/Orpheus.Net/Session/NetServer.Items.cs:231`)
при входе в область / массовых изменениях может за один такт наговорить много пачек
`PilesMessage` (по 48 записей) + `PileGoneMessage` — всплеск трафика UDP на персонажа.
Мешает приёмке нагрузки (40 врагов + добыча с E3-3b — куч теперь заметно больше).
Разблокирует: приёмку 2.16 (нагрузка), стабильность сети этапа 4.

## Что делаем
1. Прочитать `SendPilesTo` и учёт `pl.SentPiles`: посчитать, сколько сообщений на игрока
   за такт реально уходит при входе в область 200+ куч (замер — тест или лог `PileMessagesSent`).
2. Ввести потолок сообщений куч на игрока за такт (константа, порядка 2; свериться с
   `PilesEnterPerTick` :48 — она ограничивает только «вход», диффы — нет).
3. Остаток — переносить на следующие такты (курсор/очередь в state игрока), без потери
   согласованности: `PileGoneMessage` для удалённых не терять раньше, чем куча попала клиенту.
4. Протокол не менять (38). Тесты: 200 куч в окне — за такт ≤ потолок сообщений, через
   N тактов клиент видит все кучи; при удалении кучи во время очереди — согласованность
   (нет «призраков»). Тесты в `tests/Orpheus.Tests` (файл GroundItem*/Piles*).

## Решения
- [док] Бюджет = 2 сообщения (27 + 28) на игрока за такт, как в карточке («порядка 2»). Каждая
  отправленная 28 списывает 1; каждая пачка 27 резервируется первой записью в неё (`if (batch == 0)
  budget--`), полная пачка из 48 — одно сообщение. `PilesEnterPerTick = 48` (C-035) не менялся:
  тест C-035 остаётся зелёным (новых ≤ 48 ⇒ пачек ≤ 1 за такт).
- [док] Очередь «кучи нет» живёт внутри знания игрока: в `KnownPile` поля `PendingGone/Reason/Taker`.
  Причина и поднявший вычисляются в такте обнаружения (`TakerOf` видит события только этого такта),
  куча не выпадает из `KnownPiles` до отправки 28 — «призраков» нет. Очередь уходит по возрастанию
  id (обход отсортирован). Диффы количества при нулевом бюджете не отправляются: клиент помнит
  старое `Count`, дифф придёт на следующем такте.
- [док] Возврат кучи в окно входа отменяет её `PendingGone` (OutOfView) — 28 не отправляется.
  Это проверка теста 2: после возврата новых «ушедших» нет, 188 куч остаются в знании.
- [док] Тест 2 считает 14 «ушедших» после возврата (не 12): 2 сообщения 7-го такта уходят ДО
  телепорта обратно и доставляются в следующем `Run` (клиент опрашивает канал в начале такта).
  Счёт детерминированный; суммарно 214 = 14 + 200.
- Замер до правки: 200 куч в окне входа давали до 5 пачек 27 в такт (48+48+48+48+8) на один сегмент
  входа; после — ≤ 2 сообщения за такт, полная выгрузка за ~101 такт.
