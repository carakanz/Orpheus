# E4-3b — владелец личной капли после перезапуска: id сущности не перекладывается

**Ссылки:** модуль `work/modules/save.md`, `work/modules/combat.md` (E3-3b, личная капля), `work/modules/net.md` (характер уходов).
Дефект вскрыт тестом `E43_FullWorld_CrashDuringWrite_Restarted_SameGeneration_AndWorldFacts` (карточка E4-3).

## Зачем
E3-3b завёл личную каплю: `GroundPile.Owner` = id сущности-владельца (0 = общий; сливается только
со своей, `NearestPicker` пропускает чужих, сеть не шлёт чужие). В сейве (формат 17) поле пишется
как id сущности дословно. После рестарта персонажи входят **новыми сущностями с новыми id**
(в тесте: A был 1, стал 3; `CharacterRoster` хранит движение/сумку за ключом, сущность создаётся заново).
Переложения id в записях капель нет, и id монотонны — старый id персонажа уже никогда не вернётся.

**Итог:** каждая личная капля после перезапуска становится «чужой» для всех: хозяин не может её
подобрать (`NearestPicker` пропускает), клиент её не видит (сеть не шлёт чужие). Добыча с убитых
зверей в сохранённом мире теряется для владельца. Плюс id владельца может достаться новой сущности
общего назначения (капля «привязывается» к ней).

## Что делаем
1. Выбрать устойчивый ключ владельца в сейве. Кандидаты:
   - индекс персонажа в ростере (файл `CharacterRecord[]` упорядочен «по первому входу» — стабилен
     между рестартами; капля пишет номер персонажа, при загрузке перекладывается в свежий id сущности;
     персонаж вне мира — капля общая, ждёт возвращения);
   - имя персонажа (в ростере уже есть `CharacterNames`).
2. Реализовать перекладку при загрузке в `src/Orpheus.Save/` + `src/Orpheus.Core/` (поле владельца
   кучи). Формат сохранения меняется (17 → 18): тест читает настоящий файл формата 17 прошлой
   версии, строка в `work/modules/save.md`.
3. Тест: мир с личной каплей → сейв → рестарт → A вошёл → капля принадлежит A (подбор работает,
   клиент видит), чужой B её не подбирает; старый файл 17 читается.
