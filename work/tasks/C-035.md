# C-035: пачка событий такта (урон/снаряд/взмах) + лимит куч-стрел

Ветка `task/C-035`, копия `.claude/worktrees/tc035`, база `main e729cf3`.
Пункт 8 `work/opencode_start.md` (хвосты E3-2/E3-1/C-031).

## Цель
1. Сообщения «урон» (37), «снаряд» (38), «взмах» (39) за такт — **одним сообщением на
   получателя** (новое «пачка событий» (40)), а не по сообщению на каждое событие.
   Ночной бой: десятки событий такта × несколько игроков рядом = сотни надёжных
   сообщений канала 2 за такт; пачка — одно.
2. Ограничить отправку куч-стрел за такт (хвост C-031): при входе в обзор с тысячами
   воткнувшихся стрел сервер гонит тысячи/48 ≈ десятки сообщений 27 за такт (~180 КБ).
   Лимит новых куч на игрока за такт — растягивает выгрузку обзора на несколько тактов.

Протокол: **36** (main после слияния E3-6 = 35; здесь следующее число). Сохранение не трогается.

## План
1. `Protocol/EventBatchMessage.cs`: «пачка событий» (40, канал 2): число записей 1, далее
   записи (тип 1 + тело): тип 0 — урон (тело 12: жертва u32, атакующий u32… как тело
   `DamageMessage` после номера), тип 1 — снаряд (тело как `ProjectileMessage`), тип 2 —
   взмах (тело как `StrikeMessage`). Общий лимит тела — по максимуму транспорта
   (проверить `Transport`/`BitStream` на предел дейтаграммы); переполнение пачки —
   продолжение второй пачкой в том же такте (в штатных тактах — ровно одна).
2. Сервер: сбор за такт в структуру «на получателя» (список байтов/записей):
   - `BroadcastDamage`, `BroadcastProjectiles`, `BroadcastStrike` вместо `_transport.Send`
     кладут запись в буфер получателя (радиусы рассылки — прежние: 56 т, конец снаряда
     +40 т, отказ снаряда — только стрелку);
   - `FlushEventBatches()` после такта (до/после пачек правок — как нынче канал 2
     относительно Facts: события шли Facts-каналом; пачка — тоже Facts) — по одному
     сообщению 40 на игрока; счётчик `EventBatchesSent`; старые счётчики сохранить
     (считать записи внутри пачек) — на них тесты E3-1/E3-2;
   - смерть/возрождение (24/25) — вне пачки (мало, порядок важен), порядок: пачка такта
     шла после событий такта — сохранить порядок записи внутри пачки (события такта,
     решения угроз, взмахи — как идёт сейчас).
3. Клиент: приём 40 → разбор записей → прежние `OnDamage`/снаряд/`OnStrike`; приём
   37/38/39 оставить (боты/совместимость?) — нет: протокол поднимается, одиночные
   37/38/39 остаются только там, где вне такта (решение угрозы `Decide` шлёт урон
   сразу) — решение: `Decide` тоже копит в пачку до ближайшего флеша; тест порядка.
4. Лимит куч: константа `PilesEnterPerTick` (предв. 48 — одна пачка 27 за такт на
   игрока, ~870 байт); новые кучи сверх лимита за такт не добавляются в `KnownPiles`
   (попадут в следующий такт, порядок — по номеру, детерминированно на сервере);
   «кучи нет» (28) — без лимита (мало и важно). Тест: 5000 куч-стрел, вход игрока →
   за такт ≤ N сообщений 27, за K тактов все кучи известны.
5. Тесты (`C035EventBatchTests`):
   - золотые байты пачки 40 (codec);
   - такт с 2 ударами + 1 выстрел + 1 взмах рядом → у получателя ровно 1 сообщение 40
     с 4 записями (счётчик сообщений транспорта/гард по bytes);
   - далёкий игрок — ноль (радиусы прежние);
   - порядок записей = порядок событий (два клиента, как `E31CombatFeedTests`);
   - детерминизм двух прогонов (хэш событий клиента);
   - лимит куч (выше);
   - перегруз: такт с пачкой > лимита → вторая пачка, ничего не потеряно.
