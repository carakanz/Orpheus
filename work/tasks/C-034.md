# C-034: сброс кэшей ячеек при выгрузке чанка (память клиента)

## Цель
`WorldModel.RemoveChunk` (путь выгрузки чанка у клиента) не сбрасывал записи кэшей
`RoomIndex` (метки комнат) и `LightSight` (свет с учётом стен) → при долгой игре у клиента
копятся метки всех когда-то видимых чанков (записи по 4 КБ меток + 8 КБ сетки на чанк).
Карточка из `work/backlog.md` (C-032, замечание reviewer'а 15.11).

## Что сделано
1. `RoomIndex.Drop(ChunkCoord)` и `LightSight.Drop(ChunkCoord)` — снятие записи чанка из словаря;
   `RoomIndex.EntryCount` — число записей кэша (для теста роста).
2. `WorldModel.RemoveChunk` после `_chunks.Remove` зовёт Drop для чанка и соседей окна **3 × 3**.
   Запись меток чанка X — чистая функция окна 3 × 3 вокруг X (`CellWindow.StampOf` читает
   чанки |X−C|∞ ≤ 1), поэтому снятие окна 3 × 3 верно и достаточно.
   Про штамп (замеры диагностики, вывод уточнён 18.11): `StampOf` учитывает наличие чанка
   (несозданный = −1) и его ревизию. Выгрузку чанка штамп ловит (чанк → −1), а вот цикл
   Remove+GetOrCreate на НЕЗАПИСАННОМ чанке (rev 0 → rev 0) штамп не меняет — старый кэш
   выглядит валидным. Значит явный Drop обязателен; на записанном чанке (rev > 0) штамп
   устаревание ловит сам — потому часть прежних тестов оставалась зелёной и без Drop.
3. Вызов guarded (`_rooms != null` / `_sight != null`): кэш ленивый, на сервере (чанки
   не выгружаются) не создаётся — у сервера лишних обходов нет.
4. Тесты `tests/Orpheus.Tests/C034CacheTests.cs` (5 фактов; комната 88…96 × 100…105 —
   через границу чанков x = 96: западная часть в (2,3), восточная стена x = 96 в (3,3);
   чанк (2,3) = тайлы 64…95 × 96…127, см. `Torus.ChunkBits = 5`):
   - `C034_Unload_Evicts_Rooms_And_Sight`: выгрузка + загрузка пустого чанка → метка
     ячейки дома — «снаружи», метки пересчитаны (`Rebuilds` вырос);
   - `C034_Unload_Evicts_Neighbours_Window`: метка чанка (3,3) (клетка за восточной стеной)
     при выгрузке соседа (2,3) пересчитывается — окно 3 × 3 снимает запись соседа;
   - `C034_Unload_Keeps_Labels_Outside_Eviction_Window`: чанк (4,3) за окном 3 × 3 — его
     кэшовая запись при выгрузке (2,3) НЕ снимается (страховка от over-eviction, окно 5 × 5
     на этом тесте краснеет);
   - `C034_Unload_Trims_Cache_Entries`: 8 закэшованных чанков, выгрузка (2,3) снимает ровно
     записи окна 3 × 3 (7 из 8), остаётся (4,3) — прямой тест против роста памяти клиента;
   - `C034_Repeat_Room_After_Unload_Load_Is_Identical`: после Remove+GetOrCreate метки
     чанка ровно нулевые по всему чанку (не остатки комнаты); сверка точечных меток с
     миром без выгрузки.
   21/21 зелёные (C034 + C017 — кэш комнат не сломан).

## Рework 18.11 (первый коммит c17cb7d был красным в общем прогоне)
- Причина: тесты строили комнату 100..106 × 100..105 и считали её чанк (1,1) — на самом
  деле тайлы 96…127 = чанк (3,3), комната целиком в одном чанке, границ не пересекает;
  часть проверок была ложной (зелёной без Drop). Окно 5 × 5 в `WorldModel` — ошибка
  рассуждения «чейе окно накрывает C»; верное окно — 3 × 3 (зависимость записи X только от
  |X−C|∞ ≤ 1). Переписаны координаты (комната через границу x = 96), добавлены тесты
  страховки и роста (`EntryCount`).

## Мутации
- М1 (`if (false && ...)` — не звать Drop при RemoveChunk): **1 красный** —
  `C034_Unload_Trims_Cache_Entries` (записи не снимаются, словарь растёт; `c034_m1.txt`).
  Тесты на метки остаются зелёными: штамп сам ловит замену записанного чанка (rev > 0 → 0) —
  это и есть причина, по которой рост словаря нужен мерить напрямую (`EntryCount`).
- М2 (окно 5 × 5 вместо 3 × 3): **2 красных** — `C034_Unload_Trims_Cache_Entries`
  (снимает и (4,3)) и `C034_Unload_Keeps_Labels_Outside_Eviction_Window` (`c034_m2.txt`).

(на сервере чанки не выгружаются, обход не выполняется).
