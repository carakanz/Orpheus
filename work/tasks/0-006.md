5. Аргументы по 11.2: `--world <папка> --create --seed N --size 1024|4096 --sim --bots 8:wander --ticks N --hash --record/--replay`. Мир при `--create` — пока плоский (генератор делает 0-007; оставь точку подключения `IWorldGenerator`).
6. Логи — JSON-строки по 11.6 (минимум: время, такт, уровень, категория, сообщение).
7. Хвост из backlog: `tools\ci.cmd` больше не оставляет `log.txt`.
8. Тесты `D00_Sim_*`: приёмка 0.3 — 8 ботов `wander`, 54 000 тактов на 1024²: не медленнее ×10 реального времени (замер в тест-отчёт; сам тест можно пометить `Category=Big`), повтор журнала даёт тот же хэш на каждом 300-м такте; мутация (например, порядок ботов) меняет хэш.

## Как устроено (для проверяющего)

- `src/Orpheus.Core/Sim/Simulation.cs` — такт. Порядок: 1) ввод (кадры до такта становятся текущими, без нового кадра — держится прежний); 2) движение сущностей по номеру по миру начала такта; 3) правки: запросы такта сортируются устойчиво по чанку (Y, X), внутри — по приходу; **на чанк — один `WorldModel.ApplyEdits`**, ревизия +1; 4) события (исходы правок, новые ревизии) — в буфер такта. Все буферы — заранее; переполнение очереди правок — отказ (`RequestEdit` → false).
- Проходимость для движения (`Simulation.IsBlocked`) — из таблиц `FloorId`/`ObjectId` (`05` 1.3): непроходимый пол (лава), непроходимый объект, «часть» — по якорю, дверь — по флагу записи.
- `StateHash` — канонический вид 11.5: заголовок (такт, зерно, форма, версия генератора); сущности по номеру со всеми полями; изменённые после генерации чанки (координата, ревизия, слои 3072 байта, записи построек по индексу); флаги мира — число 0 (флагов ещё нет). **Свой 64-битный, не SHA-256**: хэш считается в такте сервера раз в 10 с, а 11.6 запрещает выделения в такте; `Hasher64` (шаг `Mix(h ^ слово) + Step` на SplitMix64) не выделяет и не зависит от криптобиблиотеки платформы; цель — поймать расхождение, а не подделку. SHA-256 остаётся у файлов (3.4, 6.3).
- Журнал ввода (`InputJournal.cs`): заголовок (мир, такт начала, сущности с позициями) + записи «изменения ввода перед тактом N», «точка сверки после такта N» (общий хэш, хэш мира, хэши сущностей), «конец». Пишутся только изменения ввода: 54 000 тактов × 8 ботов = 118 КБ. Повтор сверяет точки и называет такт и сущность (или «мир»), код выхода 1.
- Боты (`src/Orpheus.Core/Bots/SimBot.cs`): `idle`; `wander` — 8 направлений или стойка (1 из 9), выдержка 0,5–3 с, генератор от SplitMix64(номер бота, система, зерно).
- Сервер: `ServerOptions` (ключи 11.2 + `--logs`, `--log кат=уровень`, `--port` — принят, сети нет), `ServerRun` (мир: `--create` → генератор → `world.base` в папке мира, без `--create` — загрузка `world.base`; без `--world` — мир только в памяти), `TickClock` (отставание до 3 тактов догоняется, больше — бросается с предупреждением «перегрузка»), `JsonLog` (`<мир>/logs/server-ГГГГ-ММ-ДД.jsonl` + консоль; поля time, tick, level, cat, msg, data).
- Пример: `dotnet run -c Release --project src/Orpheus.Server -- --world C:\tmp\w2 --create --seed 42 --size 1024 --sim --bots 8:wander --ticks 54000 --hash --record C:\tmp\inputs.bin`, затем `... -- --world C:\tmp\w2 --sim --replay C:\tmp\inputs.bin --hash`.

2. Повтор → тот же хэш на каждом 300-м такте — доказан: тест `RecordReplay` (180/180, мир от генератора сборки, повтор с папкой и без) и ручной прогон; расхождение называет такт и сущность (`Mutation_ChangedInputInJournal`).

4. CI ≤ 60 с и без `log.txt` — доказан.

**Хэш.** Свой 64-битный принимаю: шаг `Mix(h ^ слово) + C` при биективном `Mix` (финализатор SplitMix64) гарантированно меняет итог при смене любого одного слова, а для многих слов вероятность совпадения ≈ 2⁻⁶⁴. Для 180 точек сверки это с запасом; защита от подделки здесь не нужна; без выделений в такте. Канонический вид по 11.5 полный для текущих полей: заголовок (такт, зерно, форма, версия генератора); сущности по номеру — Id, Kind, Position, Carry, UnitsPerTickX10, направление, кнопки (сверено с `SimEntity`/`Mover`); изменённые чанки по (Y, X) — координата, ревизия, 3072 байта слоёв, записи построек по индексу со всеми 5 полями `BuildRecord`; флаги мира — 0.

**«0 байт в такте».** Тест `TickWithBotsEditsAndHash_AllocatesNothing` меряет `GC.GetAllocatedBytesForCurrentThread` вокруг `Step` и хэша: 3 000 тактов после прогрева, с ботами, правками и постройками в новых чанках — 0; промахов пула нет. Выделения вне такта (`RefillPools`, лог, запись журнала) — между тактами. Это честно.

**`World/` (пул словарей).** Правка аддитивная: конструктор `Chunk()` без пула остался, `Chunk(BuildMapPool?)` берёт словарь из пула только при первой постройке; при пустом пуле — как раньше. Порядок записей не зависит от словаря (`GetBuildIndices` перебирает индексы 0…1023). Тесты 0-005 (`D00_World_*`) зелёные в обоих прогонах CI.

**Замечания — исправить (исполнитель).**
1. `D00_Sim_TickOrder_InputThenMovementThenEdits` ничего не проверяет про порядок фаз. Сущность стоит на 11·U+26, край круга — 11·U+128, до стены 128 unit, а за такт она проходит 51 unit. Стена не мешает **при любом порядке** фаз. Нужно поставить сущность так, чтобы за этот такт она вошла в тайл стены (например, на 11·U+256−102−20). Тогда при правильном порядке стена не держит, а при «правки до движения» держит. Проверить мутацией.
2. Тест хэша должен ловить пропуск любого поля канонического вида. Сейчас проверены только кнопки и `Carry.X`. Нужен табличный тест: для каждого поля сущности (Id, Kind, Position.X/Y, Carry.X/Y, UnitsPerTickX10, направление, кнопки), каждого поля записи постройки (Owner, Integrity, Flags, NaturalFloor, DebrisEndTick) и для заголовка (такт, зерно, форма, версия генератора) изменить одно поле и проверить, что хэш другой. Проверить мутацией «убрать строку».

**Заметки — не блокируют (в backlog на усмотрение Продюсера).**
- В CLI-прогонах правок мира нет: хэш мира весь прогон постоянный (`17d1cf66…`). Сквозная запись и повтор мира с правками появятся, когда правки придут из ввода (кнопки); тогда нужен тест повтора с правками.
- Неизменённые чанки в хэш не идут, их задают зерно и версия генератора. Если `world.base` в папке испорчен при тех же зерне и версии, повтор этого не заметит, пока порча не скажется на движении. Нужна сверка SHA-256 снимка (3.4) при загрузке.

- Тест «порядок ботов» меняет привязку бот → сущность (другой ввод), а не порядок обхода в такте. Движение сущностей сейчас друг от друга не зависит, так что порядок обхода на хэш не влияет; тест станет значимым с коллизиями сущностей.
