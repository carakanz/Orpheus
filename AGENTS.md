# Orpheus — правила для агента (opencode читает этот файл в каждом запросе)

Эти правила — только для работы над игрой Orpheus (`C:\Users\carak\source\Orpheus`). Полные правила — `work/PRODUCER.md`; здесь то, что теряется при сжатии контекста. Составлено 13.11.2026 по разбору сессии 08–13.11 (`work/process_review_2026-11-13.md`).

## 0. Что делать — по плану

Порядок работы задаёт `work/PLAN.md` (с 13.11, слово Автора: сначала картинка и механики, инфраструктура заморожена). Очередь шагов — начало `work/next.md`. Перед шагом прочитай файл его модуля в `work/modules/` (≤ 80 строк) — вместо `docs/`. После шага обнови в нём «Состояние» и «Дальше» тем же коммитом. Задачу по сети, сохранениям или обвязке бери, только если в карточке названо, какой шаг плана она разблокирует. Каждая карточка перед слиянием проходит подагента `reviewer` (п. 3); для шагов с картинкой в карточке должны лежать снимки экрана.

Запуски игры не должны мешать Автору (слово Автора 13.11): любой запуск `Orpheus.exe`, которому нужна графика (снимки, проверки картинки), — только через `tools\run_hidden.ps1` (отдельный невидимый рабочий стол; так делает `tools\shots.ps1`). Одного `-batchmode` мало: игра всё равно создаёт окно и забирает фокус. Запуски с `-batchmode -nographics` (smoke сборки) фокус не трогают. Окно для показа Автору — только по его просьбе, с `-monitor 2 -screen-fullscreen 0`.

## 1. Не останавливаться

- Закрыл карточку — сразу бери следующую из `work/next.md`. Ход заканчивай, только если очередь пуста или всё упёрлось в Автора; тогда последняя строка ответа: `ЖДУ АВТОРА: <что именно>`.
- Запустил долгую команду в фоне — не заканчивай ход словами «жду»: займись соседним шагом (карточка, тест, журнал) или жди её результата в том же ходе.
- Вопросы Автору не блокируют работу: прими допущение, запиши в карточку и в раздел «Ждёт Автора» `work/next.md`, иди дальше.

## 2. Беречь контекст (окно 128K, сжатие каждые ~17 минут — главный тормоз)

- Файл длиннее 400 строк целиком не читать. Сначала `grep` по имени метода, потом `read` с `offset`/`limit` ±60 строк. Особенно: `Simulation.cs`, `NetServer.cs`, `NetGame.cs`, `Snapshot.cs`, `WorldSave.cs`, большие `*Tests.cs`.
- Подключён языковой сервер C# (`csharp-ls` на `Orpheus.sln`, с 13.11; работает после перезапуска opencode). Вместо чтения файла спрашивай у него: список символов файла с номерами строк, переход к определению, поиск использований, ошибки компиляции. Он видит `src/`, `tests/`, `tools/`; код клиента Unity (`client/`) — нет, там `grep`. Решение грузится ~8 с: первый ответ может быть пустым — повтори запрос.
- После сжатия не перечитывать код «для ориентира»: открой `work/codemap.md` (карта: файл → методы → строки) и раздел «Место остановки» своей карточки. Нашёл новое место — допиши строку в карту.
- Перед тем как контекст заполнится, каждые ~30 шагов обновляй «Место остановки» в карточке: что сделано, что дальше, файлы и строки. После сжатия начинай с него.
- Журналы целиком не читать: `work/status.md` — только последние 5 строк (`Get-Content -Tail 5`), `work/next.md` — первые 40 строк, `work/backlog.md` — только `grep` по теме.
- Вывод тестов и сборок — в файл в `build/logs/` (папка вне git), в контекст — только хвост (`-Tail 30`) или `Select-String "Failed|error"`. Логи в корень репозитория не класть.

## 3. Проверка — отдельным агентом, не собой

- Исполнитель свою работу не принимает. «Продюсерская приёмка» проверкой не считается.
- Перед слиянием запусти подагента `reviewer` (чистый контекст): дай ему путь к карточке, рабочую копию и диапазон коммитов. Он пишет в конец карточки раздел `## Проверка (П)` с итогом. Без «принято» — не сливать.
- Карточка, которая трогает `Simulation`, протокол, сеть или клиент, перед слиянием гоняет сборку клиента с проверками: `tools\build_client.ps1 -Backend Mono -Smoke -HostSmoke` (версию Unity скрипт берёт из проекта, E1-1). Нужен код 0. Красный host-smoke — не сливать; пороги smoke не ослаблять (сейчас он красный на `main` — P-004).
- Карточка, которая меняет протокол, формат сохранения, `Simulation` или правила боя, без раздела `## Проверка (П)` в `main` не попадает никогда.

## 4. Тесты: зелёное — значит зелёное

- Нельзя ослаблять проверку, чтобы тест позеленел (убрать `Assert`, поднять порог, сузить сценарий). Если проверка неверна — это отдельное решение: запись в «Решения» карточки с причиной и пометкой `[док]`, и о нём сказано проверяющему.
- Карточка про ботов, клиент или арт не правит правила ядра «по дороге». Нашёл дефект ядра — новая карточка.
- «Упал в общем прогоне, прошёл поодиночке» — это хрупкий тест, а не зелёный. Каждый такой случай — строка в `work/flaky.md` (тест, дата, сколько раз). Список должен уменьшаться: тест, упавший так 3 раза, чинится раньше новых карточек (карточка P-003).
- Сливать можно, если в `-All` упали только тесты из `work/flaky.md` и каждый из них прошёл поодиночке.

## 5. Журналы — коротко

- `work/status.md`: одна строка на событие, не длиннее 300 знаков: задача, итог, одно ключевое число, хэш. Подробности — в карточке.
- `work/next.md`: только невыполненное и последние 5 закрытых; старое — в `work/archive/`.
- Решения по ходу — в раздел «Решения» карточки; общие для проекта — в `work/decisions.md` (одна строка: дата, решение, причина, карточка).

## 6. Жёсткие запреты

- Код — только в ветке `task/…` и своей рабочей копии `.claude/worktrees/…`; пути абсолютные; `old/` не трогать.
- Сервер не запускать с `--public` и не открывать на все адреса; в тестах «для друзей» — `127.0.0.2`.
- Коммиты и слияния — `git commit -F` / `git merge --no-ff -F`, файл сообщения в UTF-8 без BOM. `git push --force` и `git reset --hard` на `main` — никогда.
- Unity: лицензия держится только при запущенном Unity Hub (код 198 = Hub не запущен); один процесс Unity на рабочую копию.
